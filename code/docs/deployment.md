# Deployment Guide

## Overview

The 1757-RPG monorepo deploys as three services:

| Service | Platform | Method |
|---|---|---|
| **API** (`apps/api`) | Render | Docker image via `render.yaml` |
| **Web** (`apps/web`) | Vercel | `vercel --prod` from CI |
| **Admin** (`apps/admin`) | Vercel | Manual or CI deploy |

## Production Environment Variables

Set these in the Render dashboard (API) and Vercel dashboard (Web/Admin):

| Variable | Where | Notes |
|---|---|---|
| `DATABASE_URL` | Render | Neon pooled connection (`*-pooler.*`) |
| `DIRECT_URL` | Render | Neon direct connection (for Prisma migrations) |
| `BETTER_AUTH_SECRET` | Render | Auto-generated by `render.yaml` |
| `BETTER_AUTH_URL` | Render | Full API URL (e.g. `https://api.example.com`) |
| `WEB_URL` | Render | Web client origin for CORS (e.g. `https://your-app.vercel.app`) |
| `ADMIN_URL` | Render | Admin console origin for CORS |
| `REDIS_URL` | Render | Upstash or Render Redis; omit for memory fallback |
| `NODE_ENV` | Render | Must be `production` |
| `PORT` | Render | `3001` (Render default) |
| `COOKIE_DOMAIN` | Render | `.yourdomain.com` for cross-subdomain cookies |
| `API_URL` | Vercel (build) | API origin used by `next.config.ts` rewrites — **required**, otherwise rewrites fall back to `localhost:3001` |
| `NEXT_PUBLIC_API_URL` | Vercel | API URL for server-side fetch fallbacks |
| `NEXT_PUBLIC_WS_URL` | Vercel | API URL (`https://…`) for Socket.io — the client upgrades to `wss` |

## Render Deployment

### Automatic (via render.yaml)

1. Push `render.yaml` to `main`.
2. In the Render dashboard, click **New → Blueprint** and select the repo.
3. Render reads `render.yaml` and provisions the `1757-api` service.
4. Fill in the `sync: false` variables in the dashboard.
5. Pushes to `main` auto-deploy via CI webhook.

### Manual

1. Create a **Web Service** on Render.
2. Set **Docker** as the environment.
3. Leave Root Directory empty, set Dockerfile Path to `./code/Dockerfile` and Docker Build Context to `./code`.
4. Set environment variables as listed above.
5. Configure the health check path to `/health`.

### Neon Postgres Connection Pooling

- Use the **pooled** connection string (`*-pooler.*`) as `DATABASE_URL`.
- Use the **direct** connection string as `DIRECT_URL` (for `prisma migrate` / `prisma db push`).
- Enable **connection pooling** in the Neon dashboard (PgBouncer mode).

### Redis Configuration

- **Upstash**: Paste the `rediss://` URL (TLS enabled) as `REDIS_URL`.
- **Render Redis**: Use the internal Redis URL from the Render dashboard.
- **Without Redis**: The API falls back to an in-memory snapshot store. Games will not survive a restart.

## Vercel Deployment

### Web App (one-time dashboard setup)

1. In Vercel, **Add New → Project** and import the repo.
2. Set **Root Directory** to `code/apps/web` (Vercel detects the pnpm monorepo and runs `next build` there; leave the build command untouched).
3. Set the environment variables from the table above (`API_URL`, `NEXT_PUBLIC_API_URL`, `NEXT_PUBLIC_WS_URL` — all pointing at the Render API URL).
4. Deploy. Every push to `main` deploys automatically (Vercel git integration, or the `deploy-web` CI job).

```bash
# From CI (automatic)
vercel --prod --yes --token=$VERCEL_TOKEN

# Manual
cd apps/web
vercel --prod
```

### Admin Console

Deploy `apps/admin` as a **separate Vercel project** the same way, with Root
Directory `code/apps/admin`. The CI `deploy-admin` job runs only when the
`ADMIN_VERCEL_PROJECT_ID` repo secret is set.

### Cross-origin authentication (Vercel ↔ Render)

Because the Better Auth handler runs on the Fastify API but is reached through
the Next.js rewrite proxy, the **session cookie is stored on the web (Vercel)
origin**. Two things follow:

- REST calls stay same-origin: the web client calls `/api/*` through the
  rewrite proxy, so cookies flow naturally. No extra config needed.
- **Socket.IO needs a token.** The socket connects to the API origin directly
  (`NEXT_PUBLIC_WS_URL`), where the web-origin cookie is not visible. The room
  page therefore fetches the session token from the proxied `/api/me` endpoint
  (`apps/web/lib/socket-token.ts`) and sends it in the Socket.IO handshake
  (`auth: { token }`). The API's socket middleware converts the Bearer token
  into a session (Better Auth `bearer` plugin). This is already implemented —
  no extra configuration is required, but it is the reason both the proxy
  rewrites and `NEXT_PUBLIC_WS_URL` must be set correctly.

## Docker Compose (Local Production Replica)

```bash
# Copy Docker env template
cp .env.docker .env

# Start the full stack
docker compose up -d

# Verify health
curl http://localhost:3001/health
```

Services started:
- **Postgres** (port 5432) with health check
- **Redis** (port 6379) with health check
- **API** (port 3001) with health check, depends on both

## Health Check

The `/health` endpoint returns:

```json
{
  "status": "ok",
  "uptimeSeconds": 3600,
  "timestamp": "2026-10-26T18:00:00.000Z",
  "services": {
    "database": "ok",
    "redis": "configured"
  },
  "memory": {
    "rssMb": 85,
    "heapUsedMb": 45
  }
}
```

- **200** — All services healthy.
- **503** — Database unreachable (`status: "degraded"`).

## Graceful Shutdown

The API handles `SIGTERM` and `SIGINT` signals:

1. Closes all Socket.io connections.
2. Drains in-flight HTTP requests via Fastify's close handler.
3. Exits cleanly.

This ensures zero-downtime deploys on Render (which sends `SIGTERM` before stopping the old instance).

## CI/CD Pipeline

See `.github/workflows/ci.yml`. The pipeline runs:

1. `pnpm install --frozen-lockfile`
2. `pnpm db:generate`
3. `pnpm typecheck`
4. `pnpm test`
5. `pnpm build`
6. Deploy API → Render (main only)
7. Deploy Web → Vercel (main only, `deploy-web` job)
8. Deploy Admin → Vercel (main only, `deploy-admin` job — skipped unless `ADMIN_VERCEL_PROJECT_ID` is set)

### Required GitHub Secrets

| Secret | Used By |
|---|---|
| `RENDER_SERVICE_ID` | API deploy webhook |
| `RENDER_API_KEY` | API deploy webhook |
| `VERCEL_TOKEN` | Web and admin deploys |
| `VERCEL_ORG_ID` | Web and admin deploys |
| `VERCEL_PROJECT_ID` | Web deploy (project must use Root Directory `code/apps/web`) |
| `ADMIN_VERCEL_PROJECT_ID` | Optional: admin deploy (Root Directory `code/apps/admin`) |

> Tip: instead of CI-driven deploys you can simply connect the two Vercel
> projects to the GitHub repo — Vercel then builds on every push and CI only
> runs checks. Both approaches work; don't run both for the same project.

## Cold-Start Behaviour

On Render's free/starter plan, the API spins down after ~15 minutes of inactivity. The first request takes 15-30 seconds. The web client detects this and shows a "Waking server…" loading state.

## Rollback

1. Go to the Render dashboard → **Deploys** tab.
2. Click **Rollback** on the previous healthy deploy.
3. Render instantly switches traffic to the old image.

For Vercel, use the **Deployments** tab to promote a previous deployment.
