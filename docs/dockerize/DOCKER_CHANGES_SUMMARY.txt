  ✓ packages/db/src/index.ts
    CHANGE: Added Prisma adapter detection
    
    BEFORE:
      - Always used PrismaNeon adapter
      - Failed with local PostgreSQL
      - Required Neon connection string
    
    AFTER:
      - Detects database type at runtime

      - Works with both Neon (production) and local PostgreSQL (development)
    
    BENEFITS:
      - Single codebase for both environments
      - No environment-specific code paths
      - Automatic fallback to TCP for Docker
      - Type-safe with full TypeScript support

WHAT WAS DONE
================================================================================

1. PRISMA CLIENT OPTIMIZATION
   Problem: Original code always used Neon adapter, which fails with local PostgreSQL
   Solution: Added runtime detection of database type
   Benefits: Single codebase works with both Neon and local PostgreSQL

2. MULTI-STAGE DOCKERFILES
   Problem: pnpm monorepos with hoisted node_modules are tricky to containerize

================================================================================
PROBLEMS FACED & SOLUTIONS
================================================================================

PROBLEM 1: Database Adapter Incompatibility
  Issue: Neon's WebSocket adapter fails with local PostgreSQL
  Solution: Conditional adapter selection based on database URL hostname
  Result: Single codebase works with both Neon and local PostgreSQL

PROBLEM 2: Monorepo Dependency Hoisting
  Issue: Docker's COPY command doesn't preserve pnpm's hoisted node_modules structure
  Solution: Multi-stage build that copies entire workspace and runs pnpm install in container
  Result: Hoisted node_modules correctly shared across packages

PROBLEM 3: Expo Metro Bundler on LAN
  Issue: Physical devices can't resolve localhost or 127.0.0.1 from Docker container
  Solution: Set REACT_NATIVE_PACKAGER_HOSTNAME to host machine's actual LAN IP
  Result: Physical devices can scan QR code and connect to dev server

PROBLEM 4: Database Schema Synchronization
  Issue: API container starts before database schema exists
  Solution: Docker Compose entrypoint runs pnpm db:push before starting API
  Result: Database schema automatically synchronized on startup

HOW TO USE
================================================================================

QUICK START: Backend in Docker, Frontend on Host

Windows (PowerShell):
  # Terminal 1: Start backend
  .\scripts\docker-start.ps1
  
  # Terminal 2: Start frontend
  pnpm dev

macOS/Linux:
  # Terminal 1: Start backend
  ./scripts/docker-start.sh
  
  # Terminal 2: Start frontend
  pnpm dev

EVERYTHING IN DOCKER

Windows (PowerShell):
  .\scripts\docker-start.ps1 -All

macOS/Linux:
  ./scripts/docker-start.sh --all

MANUAL DOCKER COMMANDS

  # View running services
  docker compose ps
  
  # View logs
  docker compose logs -f api
  
  # Stop all services
  docker compose down
  
  # Reset database
  docker compose down -v
  
  # Rebuild images
  docker compose build
